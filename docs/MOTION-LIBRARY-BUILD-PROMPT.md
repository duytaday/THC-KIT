This scoped integration prompt is part of the [full THC-KIT master prompt](THC-KIT-MASTER-PROMPT.vi.md). Keep its runtime/readiness contracts when continuing the broader CLI, template and evaluation work.

Consumers: the Cutroom development agent implements adapters and tests; the editing agent reads the bounded catalog/recommendation API; the pinned application model continues its existing source-bound contract. This prompt is not a replacement for that model's request or an instruction to train/promote a checkpoint.

Implement explicit supplied-render ingestion adapters that retain provider/revision claims, exact file hashes, permissions, baked-content limits and inspection requirements. Generated/third-party material remains illustration.

8. Add meaningful counterexamples: unavailable provider, missing CTA reference, unsupported aspect, too-short hold, protected-face/caption collision, stale episode/context, changed source bytes and attempted overwrite.
9. Run actual curve and application regressions, render a source-backed Motion preview/master, inspect decoded frames and preserve receipts. Exercise each external ingestion adapter with explicitly labelled technical fixtures. Mock tests do not establish an upstream render.
10. Deliver the refined prompt, applied diff, pinned inventory, test/render receipts, tracking updates and exact remaining setup/review conditions. Do not claim provider generation, listening, cache hits, public distribution or model improvement without corresponding evidence.

Acceptance: executable native Motion path; deterministic hard-gated selection; reusable templates with current-episode rebinding; all six sources indexed; output-ingestion contracts for full apps; accurate optional-native availability; no regression in source/voice/review ownership.


## Owner-confirmed readiness contract

Catalog discovery permits a clearly labelled treatment proposal, including an unavailable treatment with its missing dependencies. Automatic executable recommendations require all hard eligibility gates. Keep readiness scopes separate:

- NEEDS_RUNTIME: indexed treatment, no compatible project runtime. Show a reference preview when available, missing dependency/version and working alternatives. An installation action is project-scoped and must return actual setup evidence.
- READY_TO_RENDER: template + project runtime version/hash + asset dependencies have passed a real smoke render. Merely finding Node or an importable module is runtime presence, not this state.
- READY_FOR_SCENE: render and check the exact template version, current footage hash, scene source interval, aspect, protected regions and scene revision; record export rights. Export still enters NEEDS_REVIEW until its own full-master review is recorded.
- NEEDS_PICKUP is an independent content gate. A presenter zoom or circle does not prove a missing software click or result. Runtime readiness cannot remove this gate.

Changing the runtime, template, source bytes, source interval, scene revision or rights invalidates the matching evidence. Reimplementing a treatment with native components creates a separately identified variant with its own smoke and scene evidence. A baked external preview does not establish editable-source parity or upstream generation.

Current implementation exposes AVAILABLE/SETUP_REQUIRED/EXTERNAL_OUTPUT_IMPORT runtime capability and per-scene NEEDS_REVIEW evidence. The full readiness badge/persisted invalidation UX above is the next tracked extension; do not report it shipped until exercised end to end.
